# Agent Guide: Onboarding a New 3D Product

You are an AI agent (or engineer) who has been handed a 3D model and asked to
make it customizable: the customer designs on a 2D canvas and sees the artwork
live on the 3D model, exactly where it belongs. This guide is everything you
need. Follow it top to bottom; do not improvise around the contracts.

---

## 1. Mental model (read this first)

```
customer's 2D canvas  ──►  CanvasTexture (flipY=true)  ──►  material.map
                                                               │ samples
                                                        TEXCOORD_0 (customization UV)
                                                               │
                                                       named region meshes in the GLB
```

- The **2D design is the source of truth**; 3D is a live preview. The entire
  problem is authoring TEXCOORD_0 so that canvas position ↔ 3D position is
  predictable, upright, and unmirrored.
- **UV channel contract**: TEXCOORD_0 = customization mapping. TEXCOORD_1 =
  the model's original UV (its factory texture is repointed to channel 1, so
  the asset still renders its original look in any glTF viewer). glTF does
  NOT store UV-layer names — **channel order IS the contract**.
- **V convention**: raw glTF accessor space, v=0 at the *physical bottom*.
  The runtime canvas texture uses `flipY=true`, so canvas-top = physical-top.
- ⚠️ **trimesh flips V when loading glTF.** Every read/write that matters goes
  through raw accessors (`lib/build.py::GlbEditor.read_accessor`). If you ever
  see "everything works except V is inverted" or "err ≈ |1-2v|", this is why.
- The configurator finds meshes **by name** (`editableSurfaces[].meshName`).
  The pipeline renames/creates region meshes; you choose the names in the
  manifest.
- **Never hand-edit generated files.** Everything under `products/<id>/`
  except `source.glb`, `manifest.json`, and `faces/` is regenerated by
  `build`. Inputs are the only durable artifacts (proven: delete all outputs,
  rebuild, validation passes identically).

## 3. Step-by-step

### Step 0 — Get the physical spec
The mesh's units are arbitrary. You need ONE real measurement from the client
(e.g. "the pouch is 16 cm wide"). Record which world-axis extent it refers to.
Never invent it silently — if you must assume, flag it in the manifest
(`physical.note`), like camera-001 does.

### Step 1 — Inspect
```bash
python onboard.py inspect products/<id>     # needs products/<id>/source.glb
```
Read the per-mesh report (`inspection.json`). For each node you get:
- `shape.class`: planar / cylindrical / curved_shell / closed_or_complex
- existing-UV quality: `charts`, `coverage`, `overlap_fraction`
- `recommended_strategy` — a valid manifest strategy key you can paste in.

How to read it:
- **overlap > ~0.15** → existing UVs are unusable for customization
  (mirrored/stacked islands); you must generate new ones.
- **overlap ≈ 0, few charts, sane coverage** → `reuse_existing` is on the table.
- `cylindrical` class → `wrap`. `planar` → `planar`. Complex shells → planar
  fallback or rethink whether that region should be customizable at all.

If you don't know what the parts ARE, look at them: isolate-render nodes with
Blender headless, or open the labeler (next step) and click around. Position
+ extent in `inspection.json` (world-transformed) identify parts fast.

### Step 2 — Define regions (the human/agent judgment step)
Regions = "which faces belong together, what is it called, is it printable,
how does it unwrap". Three ways to produce the manifest:

1. **Labeler UI** (default):
   `http://localhost:8779/product-onboarding/labeler/labeler.html?model=/product-onboarding/products/<id>/source.glb`
   Click meshes (multi-part models) or face-paint (single-mesh models), name
   each region, pick strategy + axis, set the physical reference, download
   `manifest.json` into `products/<id>/`.
2. **Family heuristic script** for products you onboard repeatedly
   (see `tools/classify_pouch_faces.py` → writes `faces/*.json` used by
   `select: {"by": "faces", "node": ..., "facesFile": ...}`).
3. **Write the manifest by hand** (fine for by-nodes selection).

Decision rules you must make here:
- **Customizable or not?** Non-customizable regions pass through the pipeline
  byte-identical (hardware, lenses, zippers). When unsure, leave it
  non-customizable — you can always add it later.
- **Strategy per region** (they mix freely in one product):
  - `wrap` — anything printed around an axis (labels, sleeves, body wraps).
    Set `seam_deg` so the seam lands where nobody looks (usually the back:
    seam is at angle θ measured in the plane perpendicular to `axis`,
    atan2-style from the first non-axis coordinate).
  - `planar` — flat-ish panels, plates, badges.
  - `reuse_existing` — clean authored UVs (check overlap first). Supply
    `physicalWidthCm/HeightCm` or accept a bounding-box estimate.
- **Layout mode** (`manifest.layout`) — the customer-facing 2D shape:
  - `{"mode": "shared", "order": [...]}` → ONE continuous canvas, panels side
    by side, upload-once-drag-anywhere. Use when the regions are physically
    one printed sheet (pouches, wraps, boxes). This is what packaging clients
    expect (a dieline).
  - `{"mode": "separate"}` (default) → one canvas/tab per region. Use when
    regions are separate print jobs (camera body wrap vs. name plate).

### Step 3 — Build
```bash
python onboard.py build products/<id>
```
Produces: `product-customizable.glb`, `regions.json`, `product.json`,
`uv-template-*.svg/png`, `diagnostic-*.png` — including an auto-generated
**dieline** (region outlines derived from UV boundaries, crease lines at
panel boundaries) and auto camera presets with per-region close-ups.

### Step 4 — Validate (the fix loop)
```bash
python onboard.py validate products/<id>    # must end passed: true
```
This is math, no rendering: UV range/overlap, strategy reproducibility from
the exported bytes, canvas→3D probes, orientation, **chirality** (text must
read left-to-right from outside), TEXCOORD_1 + texture-channel preservation,
non-customizable nodes unchanged, and the **dieline quality gate** (guides
present, in-bounds, smooth, one safety outline per region) — a product cannot
validate with unprofessional-looking 2D guides.

Expected first-run failures and their one-line fixes:
| Failure | Fix in manifest |
|---|---|
| `not mirrored (chirality)` | toggle `flip_u` on that region |
| `high-v is physical-top` | toggle `flip_v` |
| probes miss / land weird | wrong `axis`, or region selection includes stray faces |
| `strategy reproducible` fails | you edited generated files by hand, or wrong node selected |

Change the manifest → `build` → `validate` again. Converges in 1–2 rounds.

### Step 5 — Visual proof (production texture path)
```bash
node harness/shoot.mjs /product-onboarding/products/<id> products/<id>/validation/harness.png
```
This drives real three.js (GLTFLoader → CanvasTexture → material.map on the
named meshes), places a magenta logo at strategic canvas positions, and
**asserts** per-view pixel visibility (exit 2 on failure). Then LOOK at the
PNG: letters upright? placements where you predicted? seam hidden?

### Step 6 — Integrate into the app
```bash
python onboard.py integrate products/<id>
```
copies the GLB to `public/models/` and `product.json` to
`src/lib/configurator/generated/`. Then in
`src/lib/configurator/product-config.ts` add three lines:
```ts
import xJson from "./generated/<id>.product.json";
export const xProduct = onboardedProduct(xJson as unknown as typeof cameraProductJson);
// ...and inside PRODUCTS:  [xProduct.id]: xProduct,
```
`npm run typecheck`, then open `/studio?product=<id>` and add text/artwork
through the real editor. That's the definition of done.

## 4. Manifest reference

```jsonc
{
  "id": "mug-001",
  "name": "Classic Mug",
  "source": "source.glb",
  "physical": {
    "reference": {"extent": "x", "cm": 12.0},   // ONE known world-extent
    "note": "client spec / assumption flag"
  },
  "template": {"pxPerCm": 40, "minEditorPx": 480},
  "modelYOffset": 0,
  "materialProfile": "glossy-laminate",          // optional, this is default
  "layout": {                                    // optional; default separate
    "mode": "shared",
    "order": ["front", "bottom", "back"],
    "surfaceId": "film", "surfaceLabel": "Printed film"
  },
  "regions": [
    { "id": "body", "label": "Body", "customizable": true,
      "meshName": "BODY_PRINT",                  // 3D mesh name = contract
      "select": {"by": "nodes", "nodes": ["Object_3"]},
      //   or   {"by": "faces", "node": "Mesh_0", "facesFile": "faces/body.json"}
      //   or   {"by": "faces", "node": "Mesh_0", "faces": [1,2,3]}
      "strategy": {"type": "wrap", "axis": "y", "seam_deg": 270, "flip_u": true}
      //   or   {"type": "planar", "axis": "z", "flip_u": false, "flip_v": false}
      //   or   {"type": "reuse_existing", "physicalWidthCm": 9, "physicalHeightCm": 9}
    },
    { "id": "rest", "label": "Hardware", "customizable": false,
      "select": {"by": "rest"} }                 // preserved byte-identical
  ]
}
```

## 5. Hard limits (fail loudly — plan around them)

- Single-primitive meshes only (multi-material meshes: split per material in
  Blender first). One node per customizable region. No Draco sources
  (decompress with `gltf-transform` first).
- `wrap`/`planar` axes are world-axis-aligned; complex curved shells have no
  dedicated strategy yet — planar is the fallback for shallow curvature.
- Scanned (AI-generated) meshes: clean debris components first
  (`experiments/uv-onboarding` has the tooling; pouch-002 used the cleaned
  mesh) and expect organic dieline outlines.
- Labeler face-paint is occlusion-safe (front faces only) but for 100k+ face
  selections write a heuristic script instead.

## 6. Extending the system

- **New strategy** (e.g. spherical): add a function to
  `lib/strategies.py::STRATEGIES` — input world-space corner positions,
  output per-corner UV (v=0 at bottom!) + physical metadata. The validator's
  reproducibility/chirality checks pick it up automatically.
- **New selector**: extend the `select.by` dispatch in `lib/build.py`.
- Keep `STATE.md` / `RUNLOG.md` updated when you change the system itself —
  they are the durable memory of why things are the way they are.

## 7. Golden rules

1. Never trust a UV you haven't validated — run `validate` after every build.
2. Never fix generated output — fix the manifest or the pipeline.
3. Visual proof is required, math proof is not optional: both, always.
4. The chirality check exists because mirroring passed every other check
   twice. Do not remove it.
5. Real Studio (`/studio?product=<id>`) is the finish line, not the harness.
6. Preserve source data: originals live on TEXCOORD_1 / untouched nodes.
7. When something looks impossible, read `RUNLOG.md` — it has probably
   happened before.
