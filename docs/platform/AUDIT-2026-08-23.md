# Vortex platform audit — 2026-08-23

This audit is tied to `main` commit `c88b3fd`. It records the state found before
the platform work on branch `feat/vortex-platform-p0-projects`. “Implemented”
means the behavior exists in executable code and is covered by a test or an
asserting harness. It does not mean every product is production-approved.

## A. Current state

### Runtime and repository shape

- Next.js 16.3 App Router, React 19.2, strict TypeScript, Tailwind 4.
- React Konva is the 2D editor; React Three Fiber/Three.js is the 3D runtime.
- The repository is a single web application plus a Python product-onboarding
  toolchain. There is no API route, database, authentication provider, object
  store, queue, or commerce backend on the audited commit.
- `src/types/configurator.ts` defines the central `DesignDocument` and resolved
  `ProductConfig` contracts. The document is product-scoped and stores a map of
  surface designs. Image and text elements share transforms in editor space.
- `src/lib/configurator/design-state.ts` owns pure document mutations and
  undo/redo history. `src/lib/configurator/use-customizer.ts` coordinates those
  mutations, canvas textures, image loading, embroidery, and browser storage.
- `src/components/configurator/DesignEditor.tsx` renders an artwork-only Konva
  layer and a separate non-printing UI layer. Its artwork canvas is the input to
  Three.js. This is the correct source-of-truth boundary and must remain.
- `src/components/configurator/Product3DViewer.tsx` routes resolved products to
  GLB, procedural carton, or procedural pouch renderers. It never owns design
  state.
- `src/lib/print/*` normalizes the same `DesignDocument`, performs physical
  preflight, renders at production PPI, embeds ICC/PDF/X metadata, and adds cut
  and crease spot-color layers. Generation currently executes in the browser
  and the result is only downloaded; no immutable server artifact exists.
- `product-onboarding/` is a mature, separate Python pipeline. It inspects a
  source GLB, applies named customization UVs, preserves original UVs, emits
  data-driven `product.json`, validates mapping/chirality/physical scale, and
  has asserting Chrome harnesses. It is not a candidate for a TypeScript
  rewrite.
- `src/lib/configurator/carton-*`, `mailer-box-spec.ts`, `unfold-*`, and
  `src/types/unfold.ts` form a coherent structural system. For procedural
  cartons, one specification drives dieline position, panel geometry, hinge
  graph, flat pose, editor guides, and 3D mapping.
- `src/lib/embroidery/*` is a physically scaled visual stitch simulation with
  generated colour/normal/roughness maps. It deliberately does not claim to be
  production digitization.

### The confirmed persistence defect

`use-customizer.ts` creates object URLs in `loadImageSource()`. Its persistence
effect then constructs a second document and intentionally keeps only text:

```ts
elements: surface.elements.filter((element) => element.type === "text")
```

The top bar nevertheless reports “Saved on this device.” A reload therefore
restores text but silently loses uploaded art and all art-specific treatments,
including embroidery settings. This is a data-loss defect, not merely a
missing convenience feature.

## C. Target architecture

The first release remains a modular monolith. Domain modules do not import
React, Konva, or Three.js. Route handlers depend on application services;
services depend on repositories/object stores; adapters depend on SQLite and
the filesystem in development.

```text
ProductDefinition + ProductVersion + OptionSelection
                         |
                         v
              ResolvedConfiguration
                         |
        +----------------+----------------+
        |                                 |
        v                                 v
 DesignProject revision              Studio runtime
        |                         (existing ProductConfig)
        v                                 |
 DesignDocument + stable asset ids        v
        |                           2D canvas -> 3D
        +----------------+----------------+
                         |
                         v
              normalized production job
                         |
                         v
         immutable ProductionArtifact snapshot
```

Initial project contracts:

```ts
type ProjectOwner =
  | { type: "guest"; id: string }
  | { type: "user"; id: string };

type DesignProject = {
  id: string;
  title: string;
  productId: string;
  productVersionId: string;
  owner: ProjectOwner;
  status: "draft" | "ready_for_preflight" | "production_ready" | "archived";
  design: DesignDocument;
  revision: number;
  previewAssetId: string | null;
  createdAt: string;
  updatedAt: string;
};

type ProjectAsset = {
  id: string;
  projectId: string;
  filename: string;
  mimeType: "image/png" | "image/jpeg" | "image/webp";
  byteSize: number;
  width: number;
  height: number;
  sha256: string;
  storageKey: string; // server-only
  createdAt: string;
};
```

`ImageElement.assetId` becomes the durable identity. `src` remains a backward-
compatible runtime locator while legacy configs/projects are migrated; server
persistence validates `assetId` ownership and never relies on an object URL.

Project updates use compare-and-swap semantics:

```text
PATCH project { expectedRevision: 7, design }
  -> UPDATE ... WHERE revision = 7
  -> revision 8 + immutable project_revisions row
  -> 409 if another writer already advanced the project
```

The client serializes writes, debounces committed edits, keeps pointer-move
transforms local, and exposes `Saved`, `Saving…`, `Unsaved changes`, `Save
failed`, and `Offline` states. The database revision is the ordering authority.

## D. Migration plan tied to files

### P0 project and asset slice

- Extend `src/types/configurator.ts` with optional stable asset identity while
  preserving existing `src` compatibility.
- Add domain contracts under `src/platform/projects/` and provider-neutral
  storage contracts under `src/platform/storage/`.
- Add a SQLite repository and filesystem object-store adapter under
  `src/server/`. Runtime storage paths stay server-only and are ignored by Git.
- Add owner resolution based on a signed, HttpOnly, same-site guest cookie.
  Route handlers never accept owner ids from request JSON.
- Add `/api/v1/projects`, project detail/update/archive/duplicate routes, and
  authorized asset upload/content routes under `src/app/api/v1/`.
- Add `src/lib/projects/client.ts` and a project/autosave hook. Refactor
  `use-customizer.ts` to load/replace a project document and queue saves only
  for committed edits.
- Update `StudioShell.tsx`, `StudioTopBar.tsx`, and `StudioPanel.tsx` for project
  context and truthful save/upload language.
- Add `/designs` as a minimal project library with resume, duplicate, and
  archive behavior.
- Preserve legacy `ProductConfig` registration and every renderer unchanged.

### Later slices

- P1 adds `src/platform/products/` and a legacy adapter that emits the existing
  `ProductConfig`; no renderer migration is required up front.
- P2 adds templates as parameterized `DesignDocument` values, not a parallel
  renderer.
- P3 adds presentation/page metadata around `EditableSurface`; a page remains
  distinct from a 3D mesh.
- P4 moves the existing print pipeline behind server-capable render adapters and
  stores checksummed artifacts against immutable project revisions.
- P5 extends authoritative carton/packaging specs and production exporters;
  Studio calls exporter interfaces rather than format-specific code.

## E. Risk register

| Risk | Control |
|---|---|
| Existing products fail after new project model | Keep `ProductConfig` and product registry unchanged; project layer wraps it |
| Object URLs leak into durable JSON | Server normalization rejects image elements without owned `assetId` and removes runtime locators |
| Guest accesses another guest project (IDOR) | Cryptographically random ids plus owner predicate on every repository operation; ids alone never authorize |
| Autosave race overwrites newer edits | serialized client queue + database revision compare-and-swap + conflict tests |
| Upload bombs or spoofed MIME | byte limit, magic/decode validation, pixel limit, supported decoded formats only, checksum |
| Path traversal | object-store keys are generated server-side and resolved under a fixed root |
| Duplicate/archive damages shared assets | explicit asset copy/reference semantics; archive is recoverable, not physical deletion |
| Print output changes while persistence changes | print normalization keeps consuming `DesignDocument`; persisted assets hydrate to authorized URLs |
| Browser/server rendering diverges | P0 previews are explicitly non-production; production remains unchanged until P4 |
| Product mapping/version drift | P0 records a version id; P1 introduces immutable published versions and adapters |
| SQLite/file storage deployed to ephemeral serverless disk | adapters fail deployment readiness unless a durable path/provider is configured; production adapter is a separate concern |
| Native dependency portability | CI uses declared Node 24 and builds dependencies in target image |
| UV/chirality regression | retain onboarding and carton math tests; do not change mapping in P0 |
| Embroidery mislabeled as production | retain current visual-only wording and treatment semantics |

## Invariants for every milestone

1. `DesignDocument` is the design truth; 3D remains derived.
2. Physical dimensions, not editor pixels, govern production.
3. An image’s stable identity is `assetId`; URLs are replaceable locators.
4. Every project write creates a monotonically ordered revision.
5. A request is authorized by owner context, never by knowledge of an id.
6. Published product versions and approved production artifacts will be
   immutable once their milestones are introduced.
7. Existing onboarding, unfolding, embroidery, and print contracts remain
   independently testable.
